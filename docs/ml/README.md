# Machine learning and hybrid diagnostics

> **Synthetic data only.** Every model in SmartDrive Guardian AI was trained and evaluated on data
> produced by the built-in simulator. The reported numbers show how well the models recover the
> simulator's own fault signatures. They are **not** evidence of real-world diagnostic accuracy,
> and no finding should be read as a confirmed mechanical fault.

Generated, reproducible artefacts in this folder:

| File | Content |
|---|---|
| [evaluation_report.md](evaluation_report.md) | All results, the rule-baseline comparison, robustness, calibration, anomaly detection, built-in scenario check, latency, failure cases |
| [model_card.md](model_card.md) | Model details, parameters, selection, thresholds, intended use and limits |
| [dataset_card.md](dataset_card.md) | Dataset composition, class distribution, missing values, splits |
| `metrics.json`, `classification_report.json` | Machine-readable metrics |
| `confusion_matrix.png`, `feature_importance.png`, `calibration.png`, `anomaly_scores.png` | Figures |

## Pipeline

```text
Telemetry samples ─► TelemetryWindow (last 60 s, 1-second bins) ─► 96 features
                                   │                                  │
                                   ├──► Rule engine (stateful)        ├──► Random Forest (multi-label)
                                   │                                  └──► Isolation Forest
                                   ▼
                     Hybrid diagnostic engine ─► findings · health score · explanations ·
                                                 recommendations ─► history + alerts (SQLite)
```

### 1. Telemetry window and features (`core/telemetry_window.py`, `ai/features.py`)

- The last 60 s of readings are binned to a 1-second grid (the last reading in each second
  wins). Training data recorded at 1 Hz and live data polled at 100 ms therefore produce the same
  features. Missing readings stay NaN; nothing is interpolated or invented.
- An analysis needs at least 20 seconds with readings, 50 % window coverage and 50 % completeness
  of the core sensors (coolant, rpm, speed, load, voltage). Otherwise the result is
  *insufficient data* and the models abstain.
- For each of the 11 sensors there are seven statistics: latest value, 10-second mean, 60-second
  mean, standard deviation, minimum, maximum and trend per minute, plus completeness. There are
  also eight relationships: oil pressure per 1000 rpm, fuel use per unit of load, voltage while the
  engine runs, coolant minus oil temperature, rpm jitter, the largest coolant jump, the share of
  time above 100 °C and window coverage. Schema version `fs-1` has 96 features.
- Features use only past readings. Scenario identifiers, labels, seeds and session ids are never
  features, and `validate_dataset` rejects any feature whose name suggests otherwise.

### 2. Dataset (`ai/dataset.py`)

- Independent simulated *sessions*, each with its own seed, driving pattern, length (5–15 min),
  sensor noise, ambient and starting engine temperature, dropouts, unsupported sensors or
  connection loss. Faults have a random onset, growth rate, maximum severity (0.4–1.0), and may be
  intermittent. Some sessions combine two faults.
- **Labels** come from the simulator's ground truth: a category is positive when its fault
  severity reached 0.3 in the last 20 s. Windows where a fault exists but is still below 0.3 are
  *ambiguous* and excluded, so a barely present fault is counted neither as normal nor as
  detectable.
- **Categories:** cooling, lubrication, fuel, electrical, sensor. *Transmission* and *brake* are not
  modelled: there is no telemetry from which they could be inferred, so the application never
  claims them.
- **Splits are by whole session** (70 / 15 / 15, stratified by session type). Neighbouring windows
  of one drive are never split between training and testing.
- Saved to `datasets/<version>/`: `metadata.json` and `sessions.json` are tracked; the large
  `dataset.npz` is git-ignored and regenerated by the training script.

### 3. Random Forest (`ai/training.py`, `ai/classifier.py`)

- A scikit-learn `Pipeline`: median imputation, then a multi-output `RandomForestClassifier`
  (`class_weight="balanced_subsample"`), with one binary output per category. Simultaneous faults
  are therefore supported natively.
- The depth and leaf size are chosen on the validation split by macro-F1. The decision threshold
  for each category is the highest-F1 threshold whose validation precision is at least 0.9.
  Outputs from 60 % of the threshold upwards are reported as *uncertain*.
- Probabilities are the forest's own output and are not recalibrated. Calibration is measured
  instead: Brier score, expected calibration error and a reliability diagram. The interface calls
  them model output, never failure probabilities.
- **Abstention:** the model returns no labels when data is insufficient or stale, or when more
  than 25 % of the available features lie outside the training range (0.5th–99.5th percentile of
  the training data, widened by 10 % of that range on each side). In that case the input is out
  of distribution.
- **Lubrication** cannot be assessed when the vehicle reports no oil pressure. The category is
  then omitted and shown as *not assessed*, never as negative.

### 4. Isolation Forest (`ai/anomaly_detector.py`)

- Trained only on *normal* training windows. It uses a subset of physically meaningful features
  so that anomaly scores reflect the vehicle state, not data-quality artefacts.
- Score = negated `score_samples`, so higher means more unusual. Thresholds are percentiles of
  validation normal scores: *low* sensitivity 99.5th, *standard* 98th, *high* 95th.
- An anomaly becomes a finding only after it persists for N consecutive analyses (default 3). The
  score is never presented as a probability of failure.

### 5. Rule engine (`core/rule_engine.py`)

Seven transparent rules: coolant temperature, coolant rise, charging voltage, oil pressure, coolant
sensor plausibility, engine-speed stability and fuel-level drop.

- Each rule has a **persistence** time before it becomes active and **hysteresis** before it
  clears. An active finding never drops severity while its condition persists.
- Rules that lack data report nothing rather than assume a value. Engine rules are skipped for
  electric vehicles.
- Thresholds (`settings.json → diagnostics.thresholds`) are conservative *simulation* defaults, not
  manufacturer specifications. The rule engine works with no models at all.

### 6. Hybrid decision policy (`services/diagnostic_engine.py`)

1. Rule findings are always kept. No model can downgrade or remove them.
2. A classifier category becomes a *model* finding only after it is positive in 2 consecutive
   analyses. Model findings are at most WARNING, because a model trained on synthetic data
   cannot confirm a fault. A model finding is marked *agrees with rule engine* when a rule reports
   the same category, and the rule finding is marked likewise.
3. A persistent anomaly is always INFORMATION. It cannot name a cause, and on its own it is
   too weak to raise alerts (see the evaluation report). It still lowers the health score and is
   stored in the history.
4. Overall severity is the highest severity among the findings. With stale data no assessment
   is made. With insufficient data the status is *insufficient data*, unless a rule could still
   evaluate.
5. Agreement between components is treated as evidence, never as proof.

### 7. Explainable AI (`ai/explainability.py`)

- **Method: exact tree-path decomposition** (the Saabas method, as used by *treeinterpreter*).
  Each tree's prediction is split into its root value plus the change at every decision node,
  attributed to that node's feature. Averaged over the forest, this gives
  `probability = base value + Σ contributions` exactly. The automated tests verify this additivity.
- **Why not SHAP.** SHAP's TreeExplainer adds `numba`, `llvmlite` and other compiled
  dependencies (well over 100 MB). These complicate the Phase 5 PyInstaller build and are not
  needed for an exact additive explanation of a Random Forest. Path attributions are not Shapley
  values: they depend on the tree structure and can favour features split near the root. That is
  documented in the interface and the model card.
- **Global importance** is *permutation importance*: the drop in validation macro-F1 when a feature
  is shuffled. It is shown separately and labelled "whole model, not this prediction".
- Explanations run in the inference worker thread, together with inference.

### 8. Experimental health score (`core/health_score.py`)

The score starts at 100 and loses points as follows:

| Cause | Deduction |
|---|---|
| Rule finding: critical / warning / information | −35 / −15 / −3 |
| Positive model output (no corroborating rule) | up to −20, scaled by output |
| Persistent anomaly / single anomalous analysis | −10 / −4 |
| Recent warning or critical alerts | −2 each, at most −10 |

Every deduction is listed in the interface. With insufficient data the score is *unavailable*.
The score is labelled experimental everywhere, and a high score never implies that the vehicle is
safe. It uses no maintenance history or trouble codes, because those are not implemented yet
(Phase 4).

## Live vehicle data (Phase 4)

The models were not retrained in Phase 4. On telemetry from a real vehicle:

| Condition | Classifier and anomaly detector | Rules |
|---|---|---|
| Live ML switched off (default) | `DISABLED` ("turned off for live vehicle data") | Run |
| Live ML on, a sensor the models were trained with is unavailable | `INCOMPATIBLE` — not run | Run |
| Live ML on, every trained sensor available, data sufficient and in range | Run, with the usual abstention (insufficient, stale, out of range) | Run |

Generic OBD-II has no oil-pressure parameter, so on real vehicles the second row applies: the
models do not produce predictions, explanations or health-score deductions. The capability
check (`obd.capabilities`) lists the sensors a vehicle cannot provide, and the engine refuses
to predict from a different input distribution rather than substituting values. Data from the
mock adapter is labelled simulated and is subject to the same check.

No real-world validation has been performed; the numbers in this folder describe synthetic
data only. Replays analyse recorded data again but never write diagnostic history.

## Model management (`ai/model_registry.py`)

- Artefacts live in `src/smartdrive/ai/artifacts/` and ship inside the package.
  `manifest.json` records the version, training date, dataset version and fingerprint, source,
  feature-schema version, parameters, training configuration, thresholds, evaluation results,
  library versions and SHA-256 hash.
- **Trusted loading only.** Joblib files are pickles and can run code, so the application loads
  only files listed in the bundled manifest whose SHA-256 matches. It never loads model files
  chosen by a user or downloaded at runtime.
- **Compatibility checks:** the artefact type, the scikit-learn `major.minor` version, the feature
  schema version and the feature names must all match. Any failure leaves that model in a
  reported state (*unavailable*, *integrity check failed* or *incompatible*), and the rules keep
  working.
- Models load once, in the background, at startup, and are reused for every analysis.
- Registered model metadata is also written to the `model_metadata` table.

## Reproducing the models (Windows PowerShell)

```powershell
.\.venv\Scripts\Activate.ps1
python scripts\train_models.py                  # dataset + training + evaluation + reports
python scripts\train_models.py --profile small --artifacts-dir out\models --reports-dir out\ml
```

The full run writes the dataset to `datasets\sdg-ds-1.1.0\`, the models and manifest to
`src\smartdrive\ai\artifacts\`, and every report and figure in this folder. Seeds are fixed
(dataset master seed 20261124, training seed 42), so the same library versions reproduce the
same dataset fingerprint and the same metrics. Different library versions can produce slightly
different forests; the manifest records the versions used.
